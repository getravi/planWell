The EPM Problem Space

Why companies build planning tools — and where they break down.

Pain

Spreadsheet sprawl. Every department runs its own model. Versions proliferate. Nobody knows which file is current.

Pain

Stale data. Actuals live in the ERP, forecasts live in Excel — the reconciliation happens manually once a quarter.

Pain

No audit trail. Who changed what assumption? Was that forecast locked before the board meeting?

Goal

Single source of truth. One model, one data layer, one version of reality that the entire company trusts.

Goal

Continuous planning. Actuals flow in automatically. Forecasts update immediately. Scenarios are compared in minutes, not days.

Goal

Grounded AI. Ask questions in natural language and get answers from live planning data — with citations.

Data Model

Star-schema design with versioned scenario data.

-- Dimensions (conformed)
time_month     (id)
department     (name, parent_name)
account        (name, parent_name)

-- Facts
actuals        (month, dept, account, value)
forecast_values(version_id, month, dept, account, value)

-- Versioning
versions       (id, name, kind, locked)
scenarios      (id, name)
scenario_formulas(scenario_id, account, formula)

-- Variables
custom_variables(id, label, kind, formula)
custom_variable_values(scenario_id, var_id, scope, value)
Design decision

Conformed dimensions. Department, account, and time are shared across actuals and forecast. A department in actuals is the same department in every scenario. No data silos.

Design decision

Versioned facts. forecast_values is keyed by version_id, not scenario name. This means the "Actuals" version stores computed forecast rows too — enabling blended views (actuals → forecast without switching contexts).

Design decision

Overrides, not copies. Scenarios store only what differs from the base — driver assumption deltas, formula overrides. The forecast engine merges these at compute time. This makes scenario creation instant and storage O(n) instead of O(n×m).

Why Hono?

Lightweight — ~9KB. First-class TypeScript, Zod integration, SSE streaming built-in. No Express baggage.

Why SQLite?

Zero infrastructure. Node 22+ ships node:sqlite natively. The entire app (including DB) is a single process — deployable as a Railway service with a Procfile.

SSE for recalc

When driver assumptions change, the server schedules a background recalculation via setImmediate and pushes a recalc-done event. The client invalidates its query cache reactively. Responsive UX even for large models.

Pure domain layer

Forecasting logic, formula evaluation, KPIs — all in src/domain/ with zero imports from Node or the framework. Tested in isolation. Swappable to any backend.

Planning Logic

Driver assumptions → formula engine → topo-sorted evaluation → forecast values.

1. Driver assumptions

Four built-in drivers per department/month: revenue growth rate, COGS % of revenue, headcount growth rate, cost per head. Plus custom input variables. Values inherit down the department hierarchy unless overridden.

2. Formula resolution

Each account has a default formula (Revenue = base × (1 + revenueGrowthRate) ^ month). Scenarios can override any formula. Actuals formulas serve as fallback. The engine resolves: scenario formula → actuals formula → default → literal.

3. Topological sort

Accounts and custom variables are topologically sorted to respect dependencies. If Net Profit = Revenue - COGS - OpEx, the engine evaluates Revenue, COGS, and OpEx first. Cycles are detected and rejected at validation time.

4. Forecast build

buildForecast iterates forecast months × departments × accounts, evaluates each formula in a context containing driver values, custom variables, and sibling account results. Output: flat forecast row per (month, dept, account).

Scenario Comparison

Side-by-side variance analysis — scenario-to-scenario, or scenario-to-prior-year-actuals.

Variance engine

compareSeries(left, right) aligns two forecast sets on (month, department, account) and computes dollar variance + variance percent. Zero-dependency pure function, tested at row level.

Prior-year comparison

Users can compare any scenario against prior-year actuals. The engine aligns the scenario's forecast months (e.g., 2026-01) with the same calendar month from prior-year actuals (2025-01). Only accounts present in both are shown — no phantom comparisons.

Visual hierarchy

Revenue line chart, variance insight cards (largest favorable/unfavorable), and a pivot grid with green/negative color coding. Monthly or quarterly granularity. Export to CSV/XLSX/PDF.

UX detail

The comparison page has a "Basis" toggle — switch between scenario-to-scenario and prior-year actuals without navigating away. The scenario picker, chart, variance cards, and grid all update reactively.

Narrative generation

One click generates an executive summary via AI: "Revenue is projected at $12.4M in the Upside scenario, 23% above the base case, driven by GPU Cloud growth of 35% and a 200bps gross margin improvement."

AI Features

Grounded FP&A analyst with tool-calling — Claude or Gemini.

Tool-calling architecture

Four tools are declared as JSON function definitions to the model:

  • getMetricSummary — KPI totals for revenue, gross margin, OpEx, headcount
  • listActuals — query actuals by month/department/account range
  • compareScenarios — variance between two scenarios
  • detectAnomalies — find statistical outliers in actuals
Multi-provider

Supports Anthropic Claude (tool_use) and Google Gemini (function calling) with automatic fallback. The model iterates up to 5 rounds of tool calls, accumulating context before answering.

Citation bars

Every AI response includes citation bars showing which tool was called and what value was returned. No black-box answers: the user sees the data provenance.

Local fallback

If no API key is configured, the system falls back to a local heuristic analyst. Answers are less nuanced, but the UI doesn't break — the tool works offline or in demo mode.

Additional Capabilities

Beyond the core — dimensions, formulas, exports, and governance.

Dimension hierarchies

Department and account dimensions support arbitrary parent-child trees. Driver values inherit down the tree — set a growth rate on "Engineering" and all sub-departments pick it up unless they set their own.

Custom variables

Input variables (per dept/month numeric values) and calculated variables (mathjs formulas referencing other variables). Topo-sorted with cycle detection at save time.

Spreadsheet-grade UX

Multi-cell paste from Excel. Arrow-key navigation. Copy grid as tab-separated. Monthly/quarterly toggles. CSV, XLSX (styled), and PDF export on every grid.

Anomaly detection

Statistical outlier detection per (department, account) series — Z-score outliers and month-over-month spikes. Flagged in the actuals grid with yellow indicators and hover tooltips.

Version governance

Versions can be locked, preventing edits to formulas and driver assumptions. Audit-friendly: locked versions preserve a point-in-time forecast. Scenario creation copies assumptions from any source version.

Live ERD

The schema page renders the full database schema as an interactive SVG entity-relationship diagram — generated from the actual table definitions, not a static image.

Design Decisions

Trade-offs made deliberately, not by accident.

SQLite over Postgres

Zero ops. No connection pooling, no migrations, no Docker. For a sandbox tool, SQLite removes every friction point. The star-schema design is identical to what you'd deploy on a warehouse — it's just backed by a file.

Synchronous recalc for actuals

When saving actuals formulas, recalculation runs synchronously before the response. This means the user never sees stale data. For scenario saves, recalc is async (SSE-driven) because scenarios trigger recomputation of all future months.

TanStack Query over Redux

Server state, not client state. Everything is a cache of server data. Mutations invalidate, SSE pushes updates, and the UI just reacts. No actions, reducers, or normalized stores to maintain.

No ORM

Prepared SQL statements are explicit, debuggable, and database-portable. The SQLite schema (in migrations.ts) is 70 lines. No migration tool, no schema sync, no hidden N+1 queries.

Domain/repository separation

The domain layer (forecast logic, formula engine, anomaly detection, baseline suggestions) imports nothing from Node or Hono. Every function accepts plain objects and returns plain objects. This means the entire planning engine can be tested without a database.

Blended actuals + forecast

The "last actuals month" setting creates a unified view: months ≤ cutoff show actuals, months > cutoff show forecast. This matches how FP&A teams actually present — one table, complete picture.

Translating to Pigment: Data Model at Scale

How the sandbox concepts map to enterprise-grade Pigment primitives.

Sandbox → Pigment

Star-schema SQLite → Pigment Lists & Metrics. Dimensions (department, account, time) become Pigment Dimension Lists with hierarchy Properties. Facts become Metrics — one Metric per measure (actuals, forecast, variance), sharing the same dimension structure. No separate "cube" concept; Pigment unifies dimensions and formulas in a single calculation engine.

Sandbox → Pigment

scenario_formulas → Pigment Metrics with conditional expressions. Formula overrides per version become Pigment Metrics using IF Version = "x" THEN ... ELSE ... patterns. Pigment's engine handles dependency resolution natively. The key modeling decision is which dimension the Metric is stored against — not OLAP cube placement.

Sandbox → Pigment

Version locking → Pigment Access Rights + Snapshots. The versions.locked flag maps to a Lock Version Boolean property on the Version Dimension. Access Rights rules use this property to set Read / No Write per Role. For permanent freeze, Pigment uses Snapshots — a point-in-time capture of up to five Applications, fully immutable and queryable.

Sandbox → Pigment

custom_variable_values → Pigment driver Metrics. Per-department, per-month overrides become data entry Metrics on Boards. Hierarchy inheritance is handled through Pigment's formula engine natively — descendant dimensions inherit ancestor values via the dimension hierarchy, no custom code.

Sandbox → Pigment

prior-year-variance → Pigment time-intelligence Metrics. Prior-year comparison becomes a Metric using time-series formula offsets. Pigment's Time Handling framework supports YoY, QoQ, period-to-date, and trailing twelve months natively — without application-level queries.

Key insight

The sandbox's star-schema IS the Pigment dimensional model. The same design (conformed dimensions, versioned data, override-based scenario deltas) scales directly. The difference is infrastructure: Pigment provides the live calculation engine, Access Rights, data connectors, and Boards — you bring the model design.

Integration Layer at Scale

From CSV import to enterprise connector architecture.

Sandbox pattern

POST /api/imports/csv — parse, upsert dimensions, replace actuals, recalculate. Simple, synchronous, single-threaded. Works for a demo dataset (hundreds of rows).

Enterprise pattern

Pigment connectors. Pre-built native connectors for NetSuite, SAP S/4HANA, Workday, Salesforce, Google BigQuery, Snowflake, Amazon Redshift — each with scheduled incremental imports. Data lands directly into Pigment Blocks (Lists and Metrics) via the Import API or connector query. No staging tier required.

Key components
  • Source mapping: map source GL accounts → planning Dimension List items. Handle chart-of-account changes via dimension property updates.
  • Validation: import-time data type checks, plus post-import validation Metrics that flag anomalies. Access Rights control promotion to "certified" status, not a separate staging tier.
  • Reconciliation: automated tie-out reports comparing source totals (via connector queries) to loaded totals in Pigment. Alert on variance beyond threshold.

Important nuance

In Pigment, data integration isn't just about loading data — it's about dimension master management. When the ERP adds a new cost center, that change must propagate through the planning model without breaking existing formulas, allocations, or reports. A robust integration layer includes dimension change management as a first-class concern.

Governance Framework

From a locked flag to enterprise-grade process control.

Sandbox governance is binary — a version is either locked or unlocked. This works for a demo but breaks down at scale:

  • Who can unlock? No role-based access control.
  • What changed between versions? No diff/history view.
  • Can we restore a previous certified version? No point-in-time recovery.

Pigment's governance model uses layered controls — not a single lifecycle state machine:

1. Version Dimension Properties
   - Lock Version (Boolean, per version)
   - Active Version (Boolean)
   - Switchover Month

2. Access Rights (per Role)
   - Read / Write on data
   - Controlled per Dimension List item
   - Controlled per Scenario

3. Audit Trail
   - Application History (all block changes)
   - Audit Logs API (SIEM integration)
   - Who changed what, when

4. Snapshots
   - Point-in-time freeze (up to 5 apps)
   - Fully immutable, queryable
   - Used for audit, board pack, restore
Role-based security

Pigment supports Workspace-level (Account Types) and Application-level (Roles) security. Access Rights rules use dimension-based Metrics with Read / Write / No Read / No Write granularity. A "Budget Owner" can edit their department's driver assumptions but not view executive compensation — controlled via a User Dimension and Access Rights Metric filtering by department hierarchy.

Process automation

Validation workflows can be built directly in Pigment using Status dimensions and Access Rights rules. When data is flagged as "Ready for Review", Access Rights lock further edits and notify the reviewer role. Pigment's API enables integration with Jira, Slack, Teams for operational routing.

Additional Enterprise Considerations

Multi-currency, allocations, and model performance.

Multi-currency

The sandbox uses a single-currency assumption (USD). In Pigment, Metrics can be dimensioned by a Currency List to store amounts in transaction, parent, and consolidated currencies. Rate types (average, closing, budget) are separate Metrics with their own data entry. Forward rate curves are driver data entered for future periods and applied via formula references in the reporting Metric.

Allocations

The sandbox has no allocation engine. Pigment supports driver-based allocation (shared costs by headcount, revenue, square footage), step-down allocations (IT → departments → products), and custom allocation rules via Metrics. Allocation results are stored in separate Metrics with full audit trail — source amount, driver value, and calculated result are all traceable.

Model performance

At enterprise scale (100+ departments, 500+ accounts, 60-month horizon, 20+ scenarios), the naive iterative evaluation in the sandbox won't perform. Pigment uses a live calculation engine — any change to inputs or formulas recalculates affected Metrics immediately, not row-by-row. Scenario comparisons, version cloning, and bulk imports are all engine-level operations, not application code. Model sparsity is managed automatically.

Key Takeaways

What the sandbox proves — and what Pigment delivers at scale.

Same dimensional model. Star-schema with conformed dimensions, versioned facts, and override-based scenario deltas — the same design works from SQLite to Pigment Lists & Metrics.

Formula engine is a modeling problem. Topo-sorted formula evaluation with dependency resolution is what every EPM engine does natively. The sandbox proves the logic; Pigment provides the infrastructure.

Grounded AI is production-ready. The tool-calling pattern with citation bars works today. At scale, the same pattern connects to Pigment's API — not just 4 tools, but any Metric query, Board drill, or workflow action.

Governance is the differentiator. A locked flag works for a sandbox. Pigment's Access Rights + Snapshots + Audit Logs — Role-based security, point-in-time freeze, complete audit trail — is what makes an EPM platform enterprise-ready.

Bottom line: The sandbox validates the model design. Pigment provides the enterprise runtime — live calculation engine, native connectors, Access Rights, Snapshots, multi-currency, and audit. The hardest problems in an EPM implementation are not technical (which platform features to use) but design-oriented: how to model the business, what dimensions matter, how to handle change over time, and how to build trust in the numbers. Those skills transfer directly.
